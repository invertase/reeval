---
title: "Measure MCP servers"
description: "See whether an MCP server helped your harness."
---

You measure an MCP server by running one task on a control with no server and a variant with the server. The effect reads `helped`, `made it worse`, or `can't tell yet`. For more information about adding MCP servers, see [Connect MCP servers](/environments/mcp).

This page uses the control `plain` and the variant `withDocs`, which adds a filesystem server.

## Run one task with and without the server

<Steps>
<Step title="Define the control and variant">

Define the control `plain` and the variant `withDocs` in the `evals/environments.ts` file. The `plain` control places the `src/user.ts` file and sets no `mcp` field. The `withDocs` variant extends `plain` under the name `with-docs`.

```ts title="evals/environments.ts"
import { defineEnvironment } from '{{ pkg }}'

export const plain = defineEnvironment('plain', {
  files: {
    'src/user.ts': 'export const id = 1\n',
  },
})

export const withDocs = plain.extendEnvironment('with-docs', ({ mcp }) => ({
  mcp: {
    docs: mcp.stdio('npx', [
      '-y',
      '@modelcontextprotocol/server-filesystem',
      '/reeval/workspace',
    ]),
  },
}))
```

`withDocs` keeps the `src/user.ts` file. The server is the only change.

</Step>
<Step title="Write the evaluation">

Declare the evaluation in the `evals/docs.eval.ts` file. The prompt doesn't name the server or `list_directory`.

```ts title="evals/docs.eval.ts"
import { evaluate, expect } from '{{ pkg }}'
import { plain, withDocs } from './environments.ts'

evaluate(
  'lists the workspace paths',
  { runs: 4, compare: { baseline: plain, variants: [withDocs] } },
  async (c) => {
    await c.send(
      'Write every path in the workspace to listing.txt, one per line.',
    )
    await expect(c, 'writes the listing').toHaveFile(
      'listing.txt',
      /src\/user\.ts/,
    )
  },
)
```

`runs: 4` gives each cell four attempts. Below four counted attempts a side, the effect reads `can't tell yet`.

</Step>
<Step title="Check the server was called">

Add a `toHaveCalledMcp` check after the file check in the `evals/docs.eval.ts` file. `toHaveCalledMcp` fails the attempt when the harness never calls the server's tool.

```ts title="evals/docs.eval.ts"
    expect(c, 'called the server').toHaveCalledMcp(
      'docs',
      'list_directory',
    )
```

The control has no server, so `called the server` fails there. For more information about the matcher, see [`toHaveCalledMcp`](/reference/matchers#tohavecalledmcp).

</Step>
<Step title="Run the comparison">

Run the evaluation with the harness named in the `reeval.config.ts` file.

```bash
npx reeval run docs
```

</Step>
<Step title="Read whether it helped">

Read the block the run prints for the evaluation. When `with-docs` passes every attempt and `plain` passes none, the block looks like this:

```text
pass             lists the workspace paths
  arm                 pass
  plain               0 of 4
  with-docs           4 of 4  helped
  check               plain   with-docs
  writes the listing  0 of 4  4 of 4
    expected file listing.txt to exist
  called the server   0 of 4  4 of 4
    expected MCP calls matching docs/list_directory, got none
```

Your counts can differ. The outcome follows the variant by default. `called the server` fails on `plain`, so read the `writes the listing` row for the task.

When `writes the listing` passes on both sides, the harness already lists the workspace, and this task cannot show what the server changed. The arm can still read `helped`, because `called the server` fails on `plain`. For more information about the rows, see [Read the results summary](/results/output).

</Step>
</Steps>
