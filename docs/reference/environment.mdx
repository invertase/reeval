title: defineEnvironment
description: Every field of an environment, the order an attempt applies them in, extend and overrides, and the fields it refuses.
---

`defineEnvironment(name, spec)` describes what an eval runs in: variables, secrets, files, rules, setup steps, skills, MCP servers and egress.

```ts title="evals/environments.ts"
import { DEFAULT_EGRESS_ALLOW, defineEnvironment } from '{{ pkg }}'

export const base = defineEnvironment('base', ({ secret }) => ({
  env: {
    NODE_ENV: 'test',
    NPM_TOKEN: secret({ hosts: ['registry.npmjs.org'] }),
  },
  files: { '~/.npmrc': 'fund=false\n' },
  setup: [{ run: 'npm ci', timeout: '5m' }],
  egress: { allow: [...DEFAULT_EGRESS_ALLOW] },
}))

export const withSkill = base.extend('with-skill', ({ file, mcp, skill }) => ({
  skills: [skill.local('./skills/house-style')],
  rules: file('./rules/house.md'),
  mcp: { docs: mcp.stdio('npx', ['-y', '@acme/docs-mcp@1.0.0']) },
}))
```

Use it with the `environment` option, or as a `compare` variant:

```ts title="evals/style.es.ts"
group('house style', { environment: base, compare: [withSkill] }, () => {
  evaluate('formats with tabs', async (t) => {
    await t.send('Format src/index.ts.')
  })
})
```

## Signature

```ts
defineEnvironment(name, spec)
defineEnvironment(name, (helpers) => spec)
```

<Property name="name" type="string">
  Letters, digits, `.`, `_`, `@`, `+` or `-`, starting with a letter or digit. It names the environment in the plan, the cell key and the record.
</Property>

<Property name="spec" type="EnvironmentSpec | ((helpers) => EnvironmentSpec)">
  The fields below, or a callback that gets `secret`, `skill`, `mcp` and `file` (see [Helpers](/reference/helpers)). The callback runs once, synchronously, when the file loads; returning a `Promise` is an error. Relative paths resolve against the file that calls `defineEnvironment`.
</Property>

It returns a frozen `Environment` with `name`, `layers` and an `extend` method.

## Fields

<Property name="env" type="Record<string, string | Secret>" optional>
  Variables for the sandbox. Secrets come from the `secret` helper; a literal string under a name containing `KEY`, `TOKEN`, `SECRET`, `PASSWORD` or `CREDENTIAL` is refused. A secret with `hosts` is brokered: the sandbox gets a placeholder, and the egress gateway swaps in the real value on requests to those hosts.
</Property>

<Property name="files" type="Record<string, string | HostFile>" optional>
  Files to write before the agent starts. Keys are workspace-relative paths, or `~/` paths in the sandbox's home, with forward slashes; an absolute path or a `..` segment is refused. Values are the content, or `file(path)` for a host file, copied byte for byte.
</Property>

<Property name="rules" type="string | HostFile" optional>
  Project rules, as markdown or `file(path)`. They're written where the harness's agent reads them: `AGENTS.md` for Cursor and Antigravity, `CLAUDE.md` for Claude Code.
</Property>

<Property name="setup" type="Array<string | { run: string, timeout?: string | number, cwd?: string }>" optional>
  Shell commands run in every attempt, in order, after files and rules and before the agent starts. They see the environment's secrets, including those sent only `to: 'checks'`. Each step's `timeout` defaults to `'5m'`; `cwd` is the directory it runs in, relative to the workspace or absolute. A step object takes only `run`, `timeout` and `cwd`. Output goes to the attempt's `setup.log`. A failing step is an infra error, not a failed eval.
</Property>

<Property name="skills" type="SkillSource[]" optional>
  Skills from `skill.local`, `skill.git`, `skill.npm`, `skill.registry` or `skill.inline`. By default the harness adapter installs them where its agent reads skills; `placement: 'workspace'` writes them into the repo's skill directory instead. See [Helpers](/reference/helpers#skill).
</Property>

<Property name="mcp" type="Record<string, McpServer>" optional>
  MCP servers, keyed by name, from `mcp.stdio`, `mcp.http` or `mcp.sse`. The agent gets them when its session starts.
</Property>

<Property name="egress" type="'allow-all' | 'deny-all' | { allow: string[] }" optional>
  Where the sandbox may connect. It replaces the policy from the config and profile `defaults`; a group's or eval's own `egress` replaces it in turn. See [Egress](/reference/egress).
</Property>

## Phase order

Every attempt applies an environment in the same order:

<Steps>
  <Step title="Image">
    The sandbox's image is ready (built once and cached; see [docker()](/reference/sandbox/docker)).
  </Step>
  <Step title="Variables, files and rules">
    The sandbox starts with `env`; ES writes `files` and `rules`.
  </Step>
  <Step title="Setup">
    `setup` steps run in order, outside the eval timeout.
  </Step>
  <Step title="Snapshot">
    ES snapshots the workspace, so files, rules and setup never show in the agent's diff.
  </Step>
  <Step title="Agent">
    The harness starts with the environment's `skills` and `mcp` servers.
  </Step>
</Steps>

## extend

```ts
parent.extend(name, spec)
parent.extend(name, (helpers) => spec)
```

`extend` is the only way to compose environments. The child's spec layers on its parent's:

| Field | When both set it |
|---|---|
| `env` | Merged by variable name; the child wins |
| `files` | Merged by path; the child wins |
| `skills`, `mcp` | Merged by name; the child wins |
| `rules` | The child's replace the parent's |
| `egress` | The child's replaces the parent's |
| `setup` | Concatenated, parent first |

Every key the child replaced is listed in the environment's `overrides` in the record (`env.NODE_ENV`, `files.src/a.ts`, `rules`, `skills.house-style`, `mcp.docs`, `egress`). A `compare` variant runs as `control.extend(variant)`, so the same rules apply there.

## Refused fields

An environment has no image of its own. What's baked into the image belongs to the sandbox:

```text
es: evals/e.es.ts: "image" isn't an environment field (defineEnvironment("e")). What's baked into the image is the sandbox's: docker({ install: … }). An environment only runs setup steps, in every attempt, with its secrets.
```

`install`, `dockerfile` and `from` get the same message, naming their own key; `image` set to a string, such as `'node:22'`, names `docker({ from: … })`. Near misses get a hint: `steps`, `exec` and `run` point to `setup`; `vars` and `secrets` to `env`; `network` and `networkPolicy` to `egress`; `skill` to `skills`; `file` to `files`; `agents` to `rules`; `use` to `extend`.

## Errors

These stop the run with exit 2, prefixed by the eval file.

| Mistake | Message |
|---|---|
| A bad name | `defineEnvironment needs a name of letters, digits, ".", "_", "@", "+" or "-" (got "my env")` |
| An unknown field | `Unknown field "steps" in defineEnvironment("e"). Did you mean "setup"?` |
| A `Promise` | `defineEnvironment("e") returned a Promise. The callback runs once at definition time and must return the environment synchronously; fetch remote content in a setup step instead.` |
| A literal secret | `env.GITHUB_TOKEN in defineEnvironment("e") is a literal string. Pass secrets with secret.fromEnv() so they're redacted and never recorded.` |
| `setup` not a list | `setup in defineEnvironment("e") must be a list` |
| A bad step | `Steps in defineEnvironment("e") are strings or { run, timeout? } objects` |
| A skill path string | `skills in defineEnvironment("e") must come from the skill helper, e.g. skills: [skill.local('./skills')] (got "./skills")` |
| An MCP object | `mcp.docs in defineEnvironment("e") must come from the mcp helper, e.g. mcp.stdio('npx', ['-y', 'server'])` |
| A bad file value | `files["a.txt"] in defineEnvironment("e") must be a string or file(path)` |
| Bad rules | `rules in defineEnvironment("e") must be markdown or file(path)` |
| A list as `environment` | `environment takes one environment, not a list (evaluate("x")). To compare environments, use compare: [a, b]; the inherited environment is the control.` |

When an attempt starts, a missing secret, a skill directory without `SKILL.md`, or a failing setup step is an infra error for that attempt. See [Errors](/reference/errors).
