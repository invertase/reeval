The `reeval` command and the `re` command run the same CLI. `-h`, `--help`, and `--version` exit 0.

## `reeval`

The end of `reeval --help` lists run arguments, the `--config` flag, and the exit code summary.

[//]: # (generated:cli-help:footer)

```text
Runs are latest, latest~N, a run id (or unique prefix), or a git SHA prefix.
Options: --config <path> (default: the nearest reeval.config.ts, or .mts, .cts, .js, .mjs, .cjs,
or reeval.yaml, in the current directory or above)
Exit codes: 0 passed, 1 failed, 2 usage/config error, 3 infra error, 4 stopped (the cloud
platform stopped the run before it finished; reeval run --cloud --resume continues it),
130 interrupted (Ctrl-C), 143 terminated (SIGTERM)
```

[//]: # (/generated:cli-help:footer)

`latest` is the most recent run, and `latest~N` counts N runs back. A run id prefix must match one run. A Git SHA prefix is 4 to 40 hexadecimal characters, matched without regard to case, and names the newest run at that commit. Resolution tries the `latest` forms, then a run id or its prefix, then a Git SHA prefix.

For more information about loading the config file, see [`--config`](/reference/configuration#--config).

For more information about environment variables, see [Environment variables](/reference/environment-variables).

## `reeval doctor`

The `reeval doctor` command reports one line per check. It checks Node, not npm. With `--online`, each harness, judge, and analysis credential check authenticates supported credentials. The supported variables are `CURSOR_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `GOOGLE_GENERATIVE_AI_API_KEY`, `OPENAI_API_KEY`, and `OPENROUTER_API_KEY`; a variable reused by separate checks may be requested more than once, and any other credential is reported as set without an authentication request. The egress check names each policy the planned attempts run under, with the environments that set it, or the config's policy when the evaluations don't load.

```text
reeval doctor                 Check Node and npm, the config, Docker and its memory, the sandbox
                              images, the keys of each harness, the judge and analysis.model,
                              egress, .gitignore and keys in .env files git sees; exit 1 on a
                              problem, each with its fix. Never prints a key
  --online                    Also try each key with one tiny authenticated request
  --json                      The checks as JSON
```

## `reeval run`

The `reeval run` command plans the evaluations and runs their attempts. `--ui`, `--log-order`, `--log-prefix`, and `--output-logs` also accept `auto`, the default. `--resume latest` equals a bare `--resume`, and `--resume latest~N` counts back over the resumable runs. `--retry-errors` takes the same refs, over the finished runs. A stopped run with a finished attempt stays resumable until `reeval clean --staging`, and `reeval run` names it once it's a day old.

### Filtering cells by trait

```bash
reeval run --trait stack=next
reeval run --trait auth=clerk --trait stack=next
```

`--trait key=value` runs only the cells whose environment's [trait](/reference/environment-helpers#environmentspec) `key` is `value`, or lists it. Repeated flags must all hold. With `compare`, a cell goes by its control's traits, so every variant runs with its control or not at all.

The filter applies after `where` and the cascade, together with a profile's [`limit.traits`](/reference/profiles#traits). `where` decides which pairs fit, whatever the run; `--trait` picks the ones to run now. The plan notes what it leaves out, as in `--trait stack=next leaves out vite-app`, and `--dry-run --json` lists those environments in each evaluation's `traitExcluded`, apart from `whereExcluded`. An evaluation, or a case, left with no cell is skipped: `no cell left: --trait stack=next matches none of vite-app`.

reeval exits with code 2 for a flag that isn't `key=value`, and for a key that no control environment of the selected evaluations defines, with the closest key it does define.

A resume plans with the settings the run started with, which its record and progress file keep as `invocation`:

| Setting | Left out | Given again |
|---|---|---|
| `--runs`, the profile (`--profile` or `REEVAL_PROFILE`) | The run's | Exits 2 unless it's the run's |
| filters, `--tag`, `--trait` | The run's | Replaces the run's for this resume, so it can leave evals out or add ones the run didn't plan |
| `--concurrency` (or `REEVAL_CONCURRENCY`) | The run's | Wins, with a note in the plan |

Attempts the run planned that a resume's filters, `--tag` or `--trait` leave out stay in the record, as they finished or as `skipped`, with a warning in the plan. While any hasn't run, the run stays `interrupted` and exits on the attempts it ran, which is the outcome `--json` gives, without being recorded (`--record` prints `Not recorded`), or stays `budget` and exits 1. A `.todo` or `.skip` counts as done, whatever the resume's filters pick: the record marks it (`todo`, `skip`). A later `reeval run --resume` runs the rest.

`REEVAL_PROFILE` and `REEVAL_CONCURRENCY` count from a `.env` file too. A run with no profile resumes with none, whatever `defaultProfile` picks now. A run an older reeval started saved no `invocation`: its resume plans with the flags given, with a note.

A filter that names a path on disk, or any absolute filter, is saved relative to the project root in posix form, with its trailing `/` kept, so the resume picks the same files from any directory. For example, `./a` typed in `evals/` is saved as `evals/a`.

### Retrying infrastructure errors

```bash
reeval run --retry-errors
reeval run --retry-errors 20261022T172927Z
```

`--retry-errors [ref]` reruns a finished (`complete`) run's attempts whose outcome is `infra_error`, a judge call its provider never answered and a turn it stopped included, with the run's saved settings, as a resume does, and writes them back into that run under the same attempt ids. Its passes and fails stay as they were. A resume restarts infra-errored attempts too, alongside the ones that never finished.

| Case | Exit | What it prints |
|---|---|---|
| The run has infra errors | The run's outcome after the retry: 0, 1 or 3 | `retried 2 errored attempts: 1 now passes, 1 fails, 0 still error` |
| The run has none | The run's own outcome: 0 or 1 | `run … has no infra errors, so --retry-errors has nothing to run again.`, and with `--json` the run's results |
| The plan changed: an infra-errored attempt is gone, an attempt is new, or a retried cell's eval source, harness, gateway, gate or judge isn't the run's | 2 | `run …'s plan changed since it ran: the eval source of evals/a.eval.ts › fails changed. …`, and the run is left as it was |
| A retried attempt resolved another environment than its cell had | 2 | `run …'s plan changed since it ran: the environment of evals/a.eval.ts › fails changed. …`, after the attempts ran; the run is left as it was |
| This reeval isn't the version the run ran on | 2 | `run … ran on reeval 0.17.2, and this is 0.18.0. … install reeval 0.17.2, or start a new run with reeval run.` |
| The run is still running | 2 | `run … is still running. Wait for it to finish, then reeval run --retry-errors …` |
| The run didn't finish | 2 | `run … didn't finish. reeval run --resume … runs the rest and retries its infra errors.` |
| Filters, `--tag`, `--trait` or `--resume` beside it | 2 | Leave them out: a retry runs every errored attempt of the run |

Each retried attempt keeps the errors it ended with before in its record's [`retries`](/reference/run-record), as `{ error, at }`. A run already recorded into the history folder is recorded again with the new outcomes, also when a `--resume` finishes an interrupted retry. A retry runs only the infra errors: an attempt the run skipped, such as one a best-of cell didn't need, stays skipped.

The record keeps the run's `plan`, `git`, `dependencies` and `stack`, and its `durationMs` is the run's plus the retry's own. In the retry line, an attempt a Ctrl-C stopped or aborted counts under `didn't finish`, and the run is then `interrupted`. `reeval run --resume` finishes it as the retry would: with the same refusals, the run's record kept, and no filters, `--tag` or `--trait`. It does so after a kill too, when the retry wrote no record, and keeps the attempts that finished before the kill. The record's [`retriedAt`](/reference/run-record) lists when each retry started.

## `reeval clean`

The `reeval clean` command deletes local debug data, the attempts' snapshots and the event streams in `.reeval/events/` of runs with no staging left, and leaves the rest of the `.reeval/runs/` directory. `--keep` defaults to 0. `--images` prunes every Docker and Podman store that answers, and with Tart installed, deletes every Tart image reeval baked a harness into that isn't running. `--staging` deletes every stopped run's staging, after putting back any record a killed resume or retry moved into it, so `reeval run --resume` can no longer finish those runs.

The command prints `Removed debug data and snapshots for <n> runs (<size>) from <directory> and .reeval/runs`, or `No debug data or snapshots to remove in <directory> or .reeval/runs`. With `--staging`, it then prints `Removed the staging of <n> stopped runs: <ids>`, or `No stopped runs in .reeval/staging to remove`. With `--images`, it then prints how many images it removed, or `No leftover images to remove`. When it deleted event streams, it ends with `Removed the event streams of <n> finished runs from .reeval/events`.

## `reeval record`

The `reeval record` command copies runs into the history directory. `--artifacts` defaults to the `history.artifacts` option, which is `evidence` by default. Before it copies a run, it scans the record and text artifacts with the same rules that masked them, and refuses on a match unless you pass `--skip-secret-scan`: the scan rechecks that masking, and a value the rules don't recognize passes it.


## `reeval show`

The `reeval show` command prints one run. An omitted run is `latest`.

[//]: # (generated:cli-help:show)

```text
reeval show [run]             One run: result blocks, --md (summary.md) or --json (the record)
  --trace                     Write its timeline as Chrome Trace Event JSON for ui.perfetto.dev:
                              attempts in lanes, with setup, turns, tool calls, checks and judge
  --out <file>                With --trace, where to write it (default .reeval/traces/<run>.json)
  --offline --all-branches    A remote history.store: read its copy without pulling first; list
                              every branch's runs, not only HEAD's
  --profile <name>            Use the history store the profile sets (also REEVAL_PROFILE)
```

[//]: # (/generated:cli-help:show)

`--trace` writes the run's timeline as [Chrome Trace Event](https://docs.google.com/document/d/1CvAClvFfyA5R-PhYUmn5OOQtYMH4h6I0nSsKchNAySU) JSON, which [Perfetto](https://ui.perfetto.dev) and `chrome://tracing` open. It works on any finished run, recorded or scratch, from any reeval version. A run still in progress has no record yet, so `reeval show` refuses its id; `reeval studio` shows it live:

| Track | What it holds |
|---|---|
| `run <run id>` | The whole run, the time before its first attempt started (planning and preflight), and an `attempts running` counter |
| `attempts`, `lane <n>` | Attempts that didn't overlap, in start order: reeval puts each attempt on the first lane free when it started, so there are as many lanes as attempts ever ran at once |

Under each attempt, each `turn <n>` sits at the time it started, with the transcript's text, reasoning and tool calls nested under it when the run kept the transcript. A call that overlaps the one it started in is cut at that call's end and carries `clippedMs`. The record holds only the totals of `setup`, the `diff`, each `check <command>` and the `judge`, so `setup` is placed from the attempt's start and the rest one after another after the last turn, and each carries `placed: estimated` in its arguments. An estimated phase may really have run elsewhere: an eval's body can call `c.exec` or `c.judge` before or between turns, and the diff is taken around each turn. Every slice's arguments hold its record fields, such as the attempt's key, outcome and phase timings.

For more information about reading one run, see [Show one run](/results/output#show-one-run).

```text
  --force                     Rebuild every image, pulling each base again (and each tart() tag),

  --registry <prefix>         Pull each image that isn't built here from this registry
```

## Exit codes

[//]: # (generated:exit-codes)

| Code | Name |
|---|---|
| 0 | `ok` |
| 1 | `failed` |
| 2 | `usage` |
| 3 | `infra` |
| 4 | `stopped` |
| 130 | `interrupted` |
| 143 | `terminated` |

[//]: # (/generated:exit-codes)

`reeval run` exits 0 on a pass, 1 on a fail, and 3 on an infrastructure error. A fail is a failed gated cell, a `budget.duration` stop, or an error outside any attempt. A harness key the model API rejects, at the session start or in a turn, or a turn the model provider stopped (out of credit, over its quota, rate limited or overloaded), makes the attempt an infrastructure error, and the turn's `c.send()` throws, so no later check or judge runs. A turn in which the key served any call isn't a rejected key, and neither is a 401 the agent's own commands get. An ungated cell can fail on a run that exits 0. Ctrl-C exits 130, and SIGTERM exits 143. Either one cancels the run and writes its record. A second Ctrl-C, or a second SIGTERM, quits at once without a record (a SIGTERM and a Ctrl-C within a second of each other, in either order, as pnpm passes it on, are one press and exit 130); a later `reeval run --resume` finishes that run.

`reeval doctor` exits 1 when a check fails. A warning alone exits 0.

`reeval compare --fail-on-regression` exits 1 on a regression, or when an added or incomparable evaluation fails on a head run that was not canceled. An evaluation with `cases` is one row, with a row per case inside it; under a pooled `passRate` or `minLift` gate, the evaluation's rate over its cases decides, not a case that flipped.

`reeval image build` exits 2 when every failed image is a usage error, or when Docker's or Tart's check refuses the host or config, else 3. In a plan with both, either one's refusal still prints beside the other's results. It exits 3 before any pull when the disk can't hold the `tart()` images it would pull, even once Tart prunes its cache: like a full disk in a Docker build, that's the machine's state, not the config.

Other errors, including a missing config file and a `tart()` image that `tart list` doesn't show, exit 2. A preflight infrastructure error or an unhandled crash exits 3.

For more information about these codes in a CI job, see [Run evaluations in CI](/evaluations/runs/ci).
