`docker()` runs each attempt in its own local Docker container. It's the default sandbox, and the only one real harnesses run in.

```ts title="evals/python.es.ts"
import { evaluate, expect } from '{{ pkg }}'
import { docker } from '{{ pkg }}/sandbox'

const python = docker({ from: 'python:3.12-slim', id: 'python' })
const withJq = docker({
  install: ['apt-get update && apt-get install -y --no-install-recommends jq'],
})

evaluate('writes fizzbuzz in python', { sandbox: python }, async (t) => {
  await t.send('Write fizzbuzz.py and unittest tests for it.')
  await expect(t.exec('python -m unittest')).toSucceed()
})

evaluate('counts orders with jq', { sandbox: withJq }, async (t) => {
  await t.send('Write count.sh, which counts orders.json entries with jq.')
  await expect(t.exec('bash count.sh')).toSucceed()
})
```

Without options, `docker()` uses ES's sandbox image for the harness, which `es image build` makes.

## Options

`image`, `from` and `dockerfile` choose the base; set at most one.

<Property name="from" type="string" optional>
  A Debian or Ubuntu based toolchain image, such as `python:3.12-slim`. On first use ES bakes Node, git and the harness on top, and caches the result.
</Property>

<Property name="dockerfile" type="string | URL" optional>
  Your Dockerfile, relative to the file that calls `docker()` (or an absolute path or `URL`). ES builds it from its directory with `--build-arg ES_BASE=<ES's sandbox image>`. Start it with `ARG ES_BASE` and `FROM ${ES_BASE}` to layer on ES's image; from any other Debian or Ubuntu base, ES bakes Node and the harness on top, as for `from`.
</Property>

<Property name="image" type="string" optional>
  An image that already has the harness baked in, used as is. ES doesn't build or pull it.
</Property>

<Property name="install" type="Array<string | { run: string, timeout?: string | number }>" optional>
  Shell commands baked onto the base in one cached layer. They run in order, as root with `HOME=/home/es` (what they put there is handed to the `es` user), from `/`, with bash, and never see secrets or the workspace: what needs either belongs in the environment's `setup`. A step's `timeout` kills it (there's none by default). Not with `dockerfile`: put the commands in it as `RUN` lines.
</Property>

<Property name="id" type="string" optional>
  The sandbox's id in cell keys and filters. Default `docker`; `docker:<last path segment of the image>` with `image` or `from`; `docker:<directory>` with a file named `Dockerfile`, or `docker:<file name>` otherwise.
</Property>

<Property name="maxConcurrent" type="number" optional>
  The most Docker sandboxes at once across the run, whatever their image.
</Property>

These set what the container runs with, not what's in its image, so changing them never rebuilds one. See [Sandbox security](/guide/sandboxes#sandbox-security).

<Property name="memory" type="string | number" optional>
  The container's memory, with no swap on top: a size such as `'4g'` or `'512m'`, or bytes. Default `'4g'`. A process that goes past it is killed with exit 137, and the container keeps running.
</Property>

<Property name="cpus" type="number" optional>
  CPUs the container may use; fractions such as `1.5` are fine. Default `2`, and never more than the Docker host has.
</Property>

<Property name="pids" type="number" optional>
  Processes and threads at once in the container. Default `1024`.
</Property>

<Property name="root" type="boolean" optional>
  Run the agent, setup steps and checks as root instead of the `es` user, with the capabilities `apt-get` needs added back (`CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETUID`, `SETGID`). Default `false`. For evals that install system packages during the attempt; baking them in with `install` needs no opt-in. Every run that uses it prints a `WARNING:` line (see [Privilege warnings](#privilege-warnings)).
</Property>

<Property name="capabilities" type="string[]" optional>
  Linux capabilities to add back, such as `['NET_RAW']`. Every other one is dropped. Default none. Every run that uses it prints a `warning:` line.
</Property>

## Privilege warnings

`root` and `capabilities` stay opt-in, and ES says so whenever a run uses them:

```text
plan  2 evals · 2 cells · 2 attempts · ~2s serial (~1s at concurrency 4)
WARNING: running as root in the sandbox: evaluate("installs deps") (docker({ root: true }))
warning: extra capabilities in the sandbox: es.config.ts (docker({ capabilities: ['NET_RAW'] }))
```

There's one line per place that set the sandbox: the config file, a profile's `defaults`, a `group` or an `evaluate`, however many evals inherit it. A sandbox with both gets both lines.

| Where | What you see |
|---|---|
| `es run` and `es run --dry-run` | The lines under the plan, before any attempt starts, in every `--ui` |
| GitHub Actions | Also a `::warning` annotation each, on the eval file for a group or eval |
| `es run --dry-run --json` | `sandboxWarnings`: `kind` (`root` or `capabilities`), `level` (`config`, `profile`, `group` or `eval`), `where`, `file`, `capabilities` and `message` |
| The run record | The same list in `plan.sandboxWarnings`, shown in `summary.md` and on the studio's run page |

## Images and caching

Each harness has its own sandbox image. `es image build` builds the images the config's evals need; `es image build --dry-run` lists them:

```text
images  4 sandbox images (nothing built: --dry-run)
docker · 15 evals
  base  evalsuite-sandbox:cursor-0.1.0  (rebuild: the harness bootstrap)
docker + install · 1 eval
  base               evalsuite-sandbox:cursor-0.1.0  (rebuild: the harness bootstrap)
  install 1 command  evalsuite-install:<base id + commands>  (build unless cached)
python · 1 eval
  from python:3.12-slim  evalsuite-sandbox:cursor-0.1.0-python-3-12-slim-1d044754  (rebuild: Node, git and the harness bootstrap on top)
docker:sqlite · 1 eval
  dockerfile docker/sqlite/Dockerfile  evalsuite-dockerfile:sqlite-9630558fd3724574  (docker build (layer cache), tagged by content hash)
  harness                              evalsuite-dockerfile:sqlite-9630558fd3724574  (inherited: FROM ${ES_BASE}, which is evalsuite-sandbox:cursor-0.1.0)
```

| Image | Tag | Rebuilt when |
|---|---|---|
| ES's sandbox image | `evalsuite-sandbox:<harness>-<adapter version>` | `es image build` (its toolchain layer is `evalsuite-sandbox-base:latest`) |
| `from` | `evalsuite-sandbox:<harness>-<version>-<image slug>-<hash>` | First use, then cached |
| `install` | `evalsuite-install:<hash of base id and commands>` | The base image's id or a command changes |
| `dockerfile` | `evalsuite-dockerfile:<name>-<hash>` | The Dockerfile or its context (less `.dockerignore`) changes, or, `FROM ${ES_BASE}`, ES's image is rebuilt (the hash has its id) |

A rebuild removes the image its tag pointed at before, unless a container or another tag still uses it, and a `from` build drops its intermediate `…-base` tag once the harness is committed, so rebuilds leave no dangling images behind.

Adapter versions: Cursor `0.1.0` (`@evalsuite/harness-cursor-sdk`, which installs `@cursor/sdk` 1.0.32), Claude Code `1.0.128` (patched, so its tag is `1.0.128-patch.5d1c985c`), Antigravity `0.1.0`. A fake harness with a `layout` uses that agent's image; without one, Cursor's.

What ES adds on top of a `from` or foreign `dockerfile` base: `bash`, `ca-certificates`, `curl`, `git`, `procps`, Node 22, npm and pnpm, the `es` user, and the workspace at `/es/workspace`. That needs `apt-get`, hence Debian or Ubuntu. Build output goes to `.es/cache/images/<tag>.log`.

Image builds don't count toward the eval timeout.

## Inside the container

Every attempt gets a fresh container with the workspace at `/es/workspace`. The agent, setup steps and checks run as `es` (uid 10001, home `/home/es`, which is where `~/` paths go), with every capability dropped, `no-new-privileges`, and the limits above. An egress gateway runs with it, as root: it enforces the [egress policy](/reference/egress), records traffic, and swaps brokered secrets and the harness's key into allowed requests. The gateway needs Node in the image, which every image ES builds has.

Every image ES builds has the `es` user. `docker({ image })` with an image that doesn't fails with `<image> has no es user to run the sandbox as. …`: rebuild it with ES, or pass `root: true`.

## Errors

| Mistake | Message |
|---|---|
| Two bases | `docker() takes one base image, but got image and from. Use image (has the harness), from (a toolchain image ES bakes the harness onto) or dockerfile.` |
| `dockerfile` and `install` | `docker() takes dockerfile or install, not both: put the install commands in the Dockerfile as RUN lines, so there's one recipe for the image.` |
| A missing Dockerfile | `docker({ dockerfile: "./Dockerfile" }): <full path> doesn't exist. Paths are relative to the file that calls docker().` |
| `env` on the sandbox | `Unknown docker() option "env". The sandbox is what's baked into the image; variables and secrets belong in defineEnvironment({ env }).` |
| A near miss | `Unknown docker() option "base". Did you mean "from"?` (also `steps`, `run`, `setup` → `install`; `file`, `build` → `dockerfile`; `user`, `privileged` → `root`; `capAdd`, `caps` → `capabilities`; `mem`, `memoryLimit` → `memory`; `cpu` → `cpus`; `pidsLimit` → `pids`) |
| An empty `install` | `docker({ install }) takes a non-empty list of shell commands, e.g. install: ['apt-get update && apt-get install -y jq'] (got [])` |
| A bad install step | `docker({ install }) commands are strings or { run, timeout? } objects (got …)` |
| `root` isn't a boolean | `docker({ root }) is true or false (got "yes")` |
| A bad capability list | `docker({ capabilities }) takes Linux capability names, e.g. capabilities: ['NET_RAW'] (got "NET_RAW")` |
| A bad `memory` | `docker({ memory }) takes a size such as '4g' or '512m', or bytes (got "4GB")` |
| A bad `cpus` or `pids` | `docker({ cpus }) takes a number of CPUs above zero, e.g. 1.5 (got 0)`, `docker({ pids }) takes a whole number of processes above zero (got 10.5)` |
| A bad install timeout | `docker({ install }) command "x": Invalid duration "5 min". Use e.g. "90s" or "15m".` (zero or negative: `A duration is more than zero`) |
| An empty `image` | `docker({ image }) must be a non-empty string (got "")` |

Before any attempt starts, ES builds every image the plan needs that isn't there, including its own image for each harness, three at a time, once each (see [Sandbox providers](/reference/sandbox/providers)). An image a group or eval sets that fails fails only its attempts; one the config sets stops the run.

| Situation | Message |
|---|---|
| Docker isn't running | `Docker is not running. Start Docker and try again.` (exit 2); on Windows, `… Start Docker Desktop (with the WSL 2 backend and Linux containers) and try again.` |
| Docker runs Windows containers | `Docker is running Windows containers, but ES's sandboxes are Linux containers. Switch Docker Desktop to Linux containers (its tray menu: Switch to Linux containers) and try again.` (exit 2) |
| An `image` that isn't there | `Docker image … not found. docker({ image }) is used as is, so pull or build it first …` |
| The config's image fails | The failure, then `The sandbox docker + install is set by es.config.ts for every eval, so nothing ran.` (exit 3) |
| A non-Debian base | `Building the toolchain layer FROM alpine:3.20 failed: ES needs a Debian or Ubuntu based image (glibc and apt-get)` |
| A failing install step | `Building the install layer (N commands) failed: install i/N exited <code>: <command>` |
| A failing Dockerfile | `Building evals/x.Dockerfile failed: a RUN step exited 42`, or BuildKit's error (`dockerfile parse error on line 2: unknown instruction: COPYY …`) |
| A harness bootstrap that fails | `Baking the Cursor CLI onto <base> failed: Bootstrap command failed …` |

Every build failure starts with that headline. A named cause follows when ES recognises one, then the failing step's own last lines (`  | …`, never ES's generated Dockerfile), then `(full log: .es/cache/images/<tag>.log)`:

```text
Building the install layer (1 command) failed: install 1/1 exited 1: dd if=/dev/zero …
out of disk space (ENOSPC): free space for Docker (docker system df, es clean --images) and rerun
  | dd: error writing '/dev/shm/fill': No space left on device
(full log: .es/cache/images/evalsuite-install-4f0c2a1e9b7d3c55.log)
```

| Cause | Named when |
|---|---|
| `out of disk space (ENOSPC)` | The output says `No space left on device` or `ENOSPC` |
| `killed (exit 137): usually out of memory` | A step exits 137 (SIGKILL, usually the kernel's out-of-memory killer) |

A registry or network error (`no such host`, `i/o timeout`, `TLS handshake timeout`, `EAI_AGAIN`, a registry `5xx` or `429`) is tried twice more, after 2 s and 8 s. A failing `RUN` or `install` step, a Dockerfile syntax error, a denied pull and a non-Debian base fail at once: they'd fail the same way again.
| An `image` without Node | `Can't keep CURSOR_API_KEY out of the sandbox: credential brokering could not start (…). The egress gateway needs Node in the image: …` |
