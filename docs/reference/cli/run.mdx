`reeval run` plans the evals that match `include` and your filters, prints the plan, runs every attempt and prints a result block per eval.

```bash
npx reeval run hello --runs 2 --ui plain
```

## Filters

```bash
npx reeval run evals/hello.eval.ts      # a file
npx reeval run "greet module"           # evals by group or name
npx reeval run "greet module › creates" # an eval in a group, by its id
npx reeval run with-house-greeting      # cells by key
npx reeval run skill antigravity        # skill.eval.ts's Antigravity cells
```

- A filter part that names an eval file picks files. Every other part picks evals by name or cell key, as a case-sensitive substring of the eval id or the cell key (`cursor:composer-2.5/with-house-greeting/docker`).
- Parts of one kind add up (OR). The two kinds narrow each other, and the plan's rows and totals count only the cells that are left.
- An eval name and a cell key, harness included, are the same kind. `reeval run claude-code:claude-sonnet-5 "greets by name"` plans every Claude Code Sonnet cell plus `greets by name` on every harness. To run one eval on one harness, filter by the eval and set a profile's [`limit.harness`](/reference/profiles#limit).
- A part that matches nothing exits 2 and names it.
- `--tag slow` keeps evals tagged `slow`, `--tag '!slow'` drops them. Repeated `--tag`s must all hold. A profile's `tags` work the same way.

## The plan line

Every run starts with it, before anything runs:

```text
plan  run 20260101T000000Z_nogit_ada-lovelace_k3f9 · 1 eval · 2 cells · 4 attempts · ~50s serial (~13s at concurrency 4)
```

The estimate is the median of each eval's recent attempts on that harness (the last 30 runs, recorded and scratch), else the harness's median, else 3 minutes an attempt. A `fakeHarness` attempt with no history is 1 second in `fakeSandbox()` and 30 seconds in `docker()` or `podman()`, the sandbox's setup. With a profile and a budget it also says which profile, why, and whether the plan fits:

```text
plan  run 20260926T174055Z_b010670_ci_vdfy · profile pr (auto: CI is set) · 18 evals · 19 cells · 19 attempts · ~57m 00s serial (~14m 15s at concurrency 4) · budget 20 attempts ✓
```

`--dry-run` adds a row per eval, then, when Docker is running, a line per sandbox image saying whether it's ready, to build, stale or missing (a `from` tag is looked up in its registry, never pulled), and stops with exit 0. Neither needs credentials, and Docker is optional.

`--dry-run --json` prints the whole plan, every cell and what was excluded, as one JSON document, with each image step's `status` and `detail`.

```text
images  4 sandbox images: 1 ready, 3 to build
  ✓ docker · cursor                     ready
  + docker+0ab0e263 · cursor + install  to build: install 1 command, not built yet
  + python · cursor                     to build: from python:3.12-slim, on python:3.12-slim (f77ac9e44ae9)
  …
```

```json
  "paths": ["evals%2Fgreetings.eval.ts › greets %25s in the house style", …]

```

`--json` prints the run's facts as one JSON document on stdout when the run ends; the progress and result blocks go to stderr. It's `suiteResult(record)` from `{{ pkg }}/view`, recomputed from the record, so `reeval show --json` still prints the record itself. The exit code is the same as without `--json`.

| Field | What |
|---|---|
| `outcome`, `tally` | The run's outcome, and outcomes per block: each `evaluate.each` case and each other eval is one, and a family whose pooled `minLift` failed is one more fail |
| `files[].evals[]` | An eval, or a pooled `evaluate.each` (`family: true`) with its `cases` and `pooled` variants |
| `across` | What the cells compare: `none`, `change` (variants), `harness` or `both` |
| `cells[]` | Each cell: counts (`infraError` and `skipped` apart from `failed`), `baseline`, `gated`, `fingerprint`, `context` (skill sources and files) |
| `checks[].outcome` | `ran` with its counts and first failure, or `not run` when no counted attempt reached it |
| `effect` | A variant against its baseline: `better`, `worse`, `same` or `unclear`. Fewer than 4 counted attempts a side is `unclear`, and so is a check the baseline never ran |
| `effort` | Median tool calls, agent time and tokens, from 4 counted attempts |
| `paths` | Every node's `path`, a stable id to cite it by: `<eval>/<case>/<harness>+<environment>+<sandbox>/checks/<label>` |

A sandbox that runs as root or with capabilities added back gets a line under the plan, one per config, profile, group or eval that set it. See [Privilege warnings](/reference/sandbox/docker#privilege-warnings).

## Resume a stopped run

`--resume` continues the same run: it keeps the run id, skips attempts that already
finished, and restarts ones that never wrote a record (or only wrote `aborted`).

```bash
npx reeval run --resume
npx reeval run --resume 20260101T000000Z_nogit_ada-lovelace_k3f9
npx reeval run --resume 20260101T0000
```

| Ref | Picks |
|---|---|
| None, or `latest` | The newest resumable run: a Stopped staging directory, or an `interrupted` or `budget` scratch record. Not `reeval show latest`, which after a crash is often the previous assembled run |
| A run id or unique prefix | That run. Git SHA prefixes aren't used: they'd pick the newest run at that commit, which is often complete |

A run is resumable when it isn't `complete` and no process for that id is still alive on this machine. The pid is what counts: a quiet heartbeat (a sleeping laptop) is still running, and resume won't destroy its containers. A second `--resume` of the same id is refused while the first CLI still holds it.

With no ref, a live leftover is named (`still running`) rather than reported as missing. `.reeval/current` points at the id from the moment the run starts, after the plan, so `--resume` can find a crash that never assembled. A usage error at plan time writes nothing.

In-flight attempts start again from the beginning, and completed ones keep their outcome, including a pass. The assembled record replaces the interrupted or budget scratch under the same id.

On GitHub Actions, the id goes to `GITHUB_OUTPUT` as `run-id` and to the step summary when the run starts, so the job log has it even if SIGKILL skips assembly. A re-run still needs the leftover staging (or interrupted scratch) restored onto the new VM.

## Before any attempt starts

| Check, in order | On failure, exit 2 without writing a run |
|---|---|
| A config is found, or `--config` names one | `No reeval.config.ts … here or above. Run reeval init.` |
| The config and every eval file load | The load error |
| `include` matches files, and filters and tags match evals | `No eval files in … match include: …` |
| `.only` isn't used in CI | |
| The plan fits `budget.attempts` | |
| The credentials of the harnesses and judge the plan uses are set, with no stray whitespace | The missing or malformed variables |
| Docker is running | |

Then it prepares every sandbox image the plan needs, three at a time, once each: see [Sandbox providers](/reference/sandbox/providers). One the config sets that can't be prepared stops the run there, exit 3 (2 for a missing `docker({ image })`); one a group or eval sets fails only the attempts that need it.

`reeval run` loads `.env.local`, then `.env`, from the config's directory, not the current one. Variables already set in your shell win, then `.env.local`, then `.env`, and the config and the evals both see them.

## Output flags

| Flag | Values | Default |
|---|---|---|
| `--ui` | `live`, `plain`, `agent` | `agent` under a coding agent, `plain` in CI or when piped, else `live` (the logs under one redrawn progress line) |
| `--log-order` | `stream`, `grouped` | `grouped` in CI, else `stream` |
| `--log-prefix` | `task`, `none` | `task`, `none` inside GitHub Actions groups |
| `--output-logs` | `full`, `errors-only`, `none` | `errors-only`: only failing attempts print their detail lines. `full` with `-v` or `-vv` |
| `-v`, `-vv` | | Off. See [Debug data](/reference/debug-data) |

Each has an environment variable: `REEVAL_UI`, `REEVAL_LOG_ORDER`, `REEVAL_LOG_PREFIX`, `REEVAL_OUTPUT_LOGS`. See [Output modes](/concepts/output).

## The result blocks

Every mode ends with a block per eval, in file-path order and then source order, then the tally, and a hint to set `analysis.model` while `analysis.model` is unset (the judge's model never stands in for it). `summary.md` and `reeval show` print the same blocks. A block starts with the eval's verdict and name:

| Verdict | The eval |
|---|---|
| `pass` | Passed its gate, with no infra error |
| `fail` | Failed its gate, or a pooled family's `minLift` |
| `infra error` | Couldn't run: a sandbox, workspace or setup step failed |
| `skipped`, `todo` | `evaluate.skip` or `evaluate.todo` |
| `not gated` | Passed with every cell ungated (a study), so it doesn't read `pass` beside `0 of 2` |

Under the name, a pass prints nothing more. A fail prints each failed check with its first assertion (`failed` on one try, `N of M` on several), `not run` for a check that never ran, an error no check explains (`error`, `judge`, `timeout`, `cancelled`, `turn error`), and `+N more passed`. A compare prints a row per arm with `N of M` and its effect, then those checks a column per arm, then an effort table from four counted tries a side; [Output modes](/concepts/output#the-layout-follows-what-the-eval-varies) has each layout.

The tally counts each eval, and each case of a family, once: `3 fail · 1 pass · 1 infra error · 2 skipped`, fails first, zeros left out. A family whose pooled `minLift` gate fails counts one more fail. Counts read `N of M`; `-v` adds each arm's difference and 95% interval. Judge scores per attempt, per-key judge rates and token usage per cell are in the studio and `reeval query`.

## What it writes

| Path | What | When |
|---|---|---|
| `.reeval/runs/<runId>.json` | The scratch run's record | Every run, including one where nothing passed |
| `.reeval/runs/<runId>/` | Its artifacts | Every run |
| The history folder | A copy of both | `--record`, `record: 'ci'` with `CI` set, or `record: 'always'` |
| `.reeval/debug/` | Each attempt's local debug data | Every run |
