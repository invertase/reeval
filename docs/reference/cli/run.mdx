`reeval run` plans the evals that match `include` and your filters, prints the plan, runs every attempt and prints a summary.

```bash
npx reeval run hello --runs 2 --ui plain
```

## Filters

```bash
npx reeval run evals/hello.eval.ts            # a file
npx reeval run "greet module"               # evals by group or name
npx reeval run "greet module › creates"     # an eval in a group, as its id reads
npx reeval run with-house-greeting          # cells by key
npx reeval run skill antigravity            # the Antigravity cells of skill.eval.ts
```

- A filter part that names an eval file picks files. Every other part picks evals by name or cell key, as a case-sensitive substring of the eval id or the cell key (`cursor:composer-2.5/with-house-greeting/docker`).
- Parts of one kind add up. The two kinds narrow each other, and the plan's rows and totals count only the cells that are left.
- A part that matches nothing exits 2 and names it.
- `--tag slow` keeps evals tagged `slow`, `--tag '!slow'` drops them. Repeated `--tag`s must all hold. A profile's `tags` work the same way.

## The plan line

Every run starts with it, before anything runs:

```text
plan  run 20260101T000000Z_nogit_ada-lovelace_k3f9 · 1 eval · 2 cells · 4 attempts · ~50s serial (~13s at concurrency 4)
```

The estimate is the median of each eval's recent attempts on that harness (the last 30 runs, recorded and scratch), else the harness's median, else 3 minutes an attempt. With a profile and a budget it also says which profile, why, and whether the plan fits:

```text
plan  run 20260926T174055Z_b010670_ci_vdfy · profile pr (auto: CI is set) · 18 evals · 19 cells · 19 attempts · ~57m 00s serial (~14m 15s at concurrency 4) · budget 20 attempts ✓
```

`--dry-run` adds a row per eval, then, when Docker is running, a line per sandbox image saying whether it's ready, to build, stale or missing (a `from` tag is looked up in its registry, never pulled), and stops with exit 0. `--dry-run --json` prints the whole plan, every cell and what was excluded, as one JSON document, with each image step's `status` and `detail`. Neither needs credentials, and Docker is optional.

```text
images  4 sandbox images: 1 ready, 3 to build
  ✓ docker            ready
  + docker+0ab0e263 + install  to build: install 1 command, not built yet
  + python            to build: from python:3.12-slim, on python:3.12-slim (f77ac9e44ae9)
  …
```

A sandbox that runs as root or with capabilities added back gets a line under the plan, one per config, profile, group or eval that set it. See [Privilege warnings](/reference/sandbox/docker#privilege-warnings).

## Resume a stopped run

`--resume` continues the same run: it keeps the run id, skips attempts that already
finished, and restarts ones that never wrote a record (or only wrote `aborted`).

```bash
npx reeval run --resume
npx reeval run --resume 20260101T000000Z_nogit_ada-lovelace_k3f9
npx reeval run --resume 20260101T0000
```

Without a ref, reeval picks the newest **resumable** thing: a Stopped staging
directory, or an `interrupted` / `budget` scratch record. That is not `reeval
show latest`. After a crash, `latest` is often the previous assembled run,
which may be complete.

`--resume <ref>` is a run id or unique prefix. Git SHA prefixes are not used:
they would pick the newest run at that commit, which is often complete.

A run is resumable when its studio heartbeat is stale (or the process is gone)
and it is not `complete`. A live run is refused. `.reeval/current` points at
the id when the run starts, after the plan, so `--resume` with no ref can find
a crash that never assembled. A usage error at plan time writes nothing.

In-flight attempts start again from the beginning of the attempt. Completed
ones keep their outcome, including a pass. The assembled record replaces the
interrupted or budget scratch under the same id.

On GitHub Actions, the id is written to `GITHUB_OUTPUT` as `run-id` and to the
step summary when the run starts, so the job log has it even if SIGKILL skips
assemble. Re-run still needs the leftover staging (or interrupted scratch)
restored onto the new VM.

## Before any attempt starts

`reeval run` checks, in order: the config and every eval file load; filters and tags match; `.only` isn't used in CI; the plan fits `budget.attempts`; the credentials of the harnesses and judge the plan will use are set (and have no stray whitespace); Docker is running. Each failure exits 2 without writing a run.

Then it prepares every sandbox image the plan needs, three at a time, once each: see [Sandbox providers](/reference/sandbox/providers). One the config sets that can't be prepared stops the run there, exit 3 (2 for a missing `docker({ image })`); one a group or eval sets fails only the attempts that need it.

`reeval run` loads `.env.local`, then `.env`, from the config's directory, not the current one: variables already set in your shell win, then `.env.local`, then `.env`. The config and the evals both see them.

## Output flags

| Flag | Values | Default |
|---|---|---|
| `--ui` | `live`, `plain`, `agent` | `agent` under a coding agent, `plain` in CI or when piped, else `live` (which prints plain for now) |
| `--log-order` | `stream`, `grouped` | `grouped` in CI, else `stream` |
| `--log-prefix` | `task`, `none` | `task`, `none` inside GitHub Actions groups |
| `--output-logs` | `full`, `errors-only`, `none` | `full` |
| `-v`, `-vv` | | Off. See [Debug data](/reference/debug-data) |

Each has an environment variable: `REEVAL_UI`, `REEVAL_LOG_ORDER`, `REEVAL_LOG_PREFIX`, `REEVAL_OUTPUT_LOGS`. See [Output modes](/concepts/output).

## The summary's eval line

An eval with several attempts shows its passes over every counted attempt, then its pass rate, which counts only the gated cells:

| Eval | Line |
|---|---|
| Every cell gated | `3/4  75%  4 attempts` |
| Some cells not gated (controls under `compare.gate: 'variants'`) | `2/4 · 100% gated  4 attempts` |

The `gated` label says the rate leaves out the ungated cells, whose failures don't fail the eval. The studio's eval history labels the rate the same way.

A single-attempt eval's line shows each judge as `pass 0.92/0.80` or
`fail 0.78/0.80`. Three or more judges collapse to the lowest score plus a
count (`fail 0.33/0.80 · 3 judges`). Token usage, when the harness reported it,
follows the turns.

An eval with several attempts also prints each judge key's passes over counted
attempts on the cell row (`login 4/5 · checkout 0/5`). A variant key shows lift
only when both sides have at least two counted attempts. The cell's tokens are
the sum of those counted attempts; a harness that reports none leaves the field
blank, never `0`.

## What it writes

Every run, including one where nothing passed, writes a scratch run to `.reeval/runs/<runId>.json` and its artifacts to `.reeval/runs/<runId>/`. `--record`, or `record: 'ci'` with `CI` set, or `record: 'always'`, also copies it into the history folder. Each attempt's local debug data goes to `.reeval/debug/`.
