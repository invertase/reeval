description: Write evals with prompts, sandbox commands, file checks, matchers and an LLM judge.

An eval gives the agent a task, then checks what it did. Here's the first `greet` eval again, the one you ran on Cursor:

```ts title="evals/hello.eval.ts"
import { evaluate, expect, group } from '{{ pkg }}'

group('greet module', () => {
  evaluate('creates a tested greet module', async (c) => {
    const turn = await c.send(
      'Create greet.js exporting greet(name) that returns "Hello, <name>!", ' +
        'and greet.test.js that tests it with node:test. No dependencies.',
    )

    await expect(turn).toHaveFile('greet.js')
    await expect(c.exec('node --test')).toSucceed()
    expect(
      await c.judge(
        "Does the agent's final message accurately describe what it changed?",
      ),
    ).toPass()
  })
})
```

It has three parts: a prompt, deterministic checks, and a question for the judge.

## Name evals with groups

```ts title="evals/hello.eval.ts"
group('greet module', () => {
  evaluate('creates a tested greet module', async (c) => { /* … */ })
  evaluate('adds a default name in a follow-up turn', async (c) => { /* … */ })
})
```

`evaluate(name, fn)` declares one eval, and `group(name, fn)` groups evals. Groups nest, and both take options as a second argument (or last). The file, groups and name make the eval's id, `evals/hello.eval.ts › greet module › creates a tested greet module`, which is how reeval tracks it across runs.

<Warning>
  Renaming an eval or its group gives it a new id, so its history starts again.
</Warning>

## Send a prompt

```ts
const turn = await c.send('Create greet.js exporting greet(name).')
turn.text        // the agent's final message
turn.status      // 'completed', 'aborted' or 'error'
turn.diff.files  // [{ path: 'greet.js', status: 'added' }]
```

`c.send` runs one agent turn and resolves when it ends. The first call starts the sandbox and the agent session. The `Turn` it returns doesn't change afterwards, so you can check it later.

## Run commands in the sandbox

```ts title="evals/guide.eval.ts"
evaluate('passes its own tests', async (c) => {
  await c.send('Create greet.js and greet.test.js. No dependencies.')

  const result = await c.exec('node --test')
  expect(result.exitCode).toBe(0)
  expect(result.stdout).toContain('pass 1')
})
```

`c.exec` runs a shell command in the eval's workspace, in the same container as the agent. It returns `{ exitCode, stdout, stderr }`. `await expect(c.exec(cmd)).toSucceed()` is the short form: it fails on a non-zero exit and prints the command's stderr and stdout.

## Check files

```ts title="evals/guide.eval.ts"
evaluate('writes a module', async (c) => {
  const turn = await c.send('Create greet.js exporting greet(name).')

  await expect(turn).toHaveFile('greet.js', /export function greet/)
  const source = await c.readFile('greet.js')
  expect(source).not.toContain('require(')
})
```

`toHaveFile(path, pattern?)` checks a file exists and, optionally, matches a string or regular expression. `c.readFile` returns the contents, or `null` when there's no such file. Paths are relative to the workspace, or start with `~/` for the home directory.

## Await the matchers

`toHaveFile` and `toSucceed` read from the sandbox, so they return promises. Always `await` them:

```ts
expect(turn).toHaveFile('nope.js')        // wrong: not awaited
await expect(turn).toHaveFile('nope.js')  // right
```

```text
Summary
 evals/guide-unawaited.eval.ts
   ✗ unawaited     45ms  1 turn
…
 ✗ evals/guide-unawaited.eval.ts › unawaited
   Error: expected file nope.js to exist

   expect(…).toHaveFile() wasn't awaited. Its check is async: write `await expect(…).toHaveFile()`.
```

<Warning>
  An unawaited matcher fails its eval even when its check passes, so a missing `await` shows up as a failure that tells you to add it.
</Warning>

`toPass()` is synchronous: await `c.judge`, not the `expect`. So are `toHaveSearched(query?)` and `toHaveFetched(url?)`, which check a turn's web calls. The usual `expect` [matchers](/reference/matchers) (`toBe`, `toContain`, `toMatch`…) work too.

## Ask the judge

```ts
const verdict = await c.judge('Is the change minimal?', { threshold: 0.9 })
expect(verdict).toPass()
```

The judge answers a yes/no question about the latest turn. It sees the task, the agent's final message, the changed files and the diff. It returns `{ verdict, score, threshold, question, model }`, and passes when the probability of "yes" is at least the threshold (0.8 by default). Set the model in `reeval.config.ts`, as in [Your first real run](/guide/first-real-run); [Judges](/concepts/judges) covers writing good questions.

## Choose checks or the judge

| Use | When the answer is | Example |
|---|---|---|
| `c.exec`, `toSucceed` | Something a command can decide | `node --test`, a build, a script's output |
| `toHaveFile`, `c.readFile` | In the files | A config key, an import, no `require(` |
| `c.judge` | A matter of judgement | "Does the message describe the change?" |

Prefer checks: they're exact, free and never change their mind. Use the judge for what no command can decide, and keep each question to one thing.

## Tag evals

```ts title="evals/guide.eval.ts"
group('greet module', { tags: ['smoke'] }, () => {
  // …
})
```

```bash
npx reeval run --tag smoke        # only evals tagged smoke
npx reeval run --tag '!slow'      # everything but slow
```

Tags add up from groups to evals. Repeat `--tag` to combine filters; each one must match.

## Skip, focus and plan evals

```ts title="evals/guide.eval.ts"
evaluate.skip('greets in French', async (c) => {
  await c.send('Add greetFr(name).')
})
evaluate.todo('greets a list of names')
```

```text
Summary
 evals/guide.eval.ts
   greet module
     ✓ writes a module            57ms  1 turn
     ✓ passes its own tests      121ms  1 turn
     ↓ greets in French        skipped
     ↓ greets a list of names  todo
```

`.skip` keeps an eval without running it, and `.todo(name)` notes one to write, shown as todo in the plan, the summary, the record and the studio. `.only` runs only the marked evals in a file while you work on them; it's an error when `CI` is set, so it can't slip into a pipeline. `group` has all three too.
