title: Sandboxes and toolchains
description: Run the agent on Python, your own Dockerfile or ES's image with extra tools, using docker().
---

Every attempt runs in a fresh Docker container. `docker()` with no options uses ES's image: Node 22, git and the harness's agent. When the task needs another toolchain, give the sandbox another base.

```ts
import { docker } from '{{ pkg }}/sandbox'

docker()                                        // ES's image
docker({ from: 'python:3.12-slim' })            // ES adds Node, git, the agent
docker({ install: ['npm i -g firebase-tools@14'] }) // extra tools
docker({ dockerfile: './sandbox/Dockerfile' })  // your own, from this file
docker({ image: 'ghcr.io/acme/agent:1' })       // already has the agent
```

A sandbox has one base (`image`, `from` or `dockerfile`), and optionally `install` commands on top. What's baked into the image belongs to the sandbox. What each attempt adds, such as files, secrets and setup steps, belongs to the [environment](/guide/environments).

## Start from a toolchain image

```ts title="evals/python.es.ts"
import { evaluate, expect } from '{{ pkg }}'
import { docker } from '{{ pkg }}/sandbox'

evaluate(
  'writes and tests fizzbuzz in python',
  { sandbox: docker({ from: 'python:3.12-slim', id: 'python' }) },
  async (t) => {
    await t.send(
      'Write fizzbuzz.py with a function fizzbuzz(n) returning the usual ' +
        'FizzBuzz string for n, and test_fizzbuzz.py with unittest tests ' +
        'for 3, 5, 15 and 7. Standard library only.',
    )
    await expect(t.exec('python3 --version')).toSucceed()
    await expect(t.exec('python3 -m unittest -q')).toSucceed()
  },
)
```

`from` takes any Debian or Ubuntu based image. ES bakes Node, pnpm, git and the harness's agent on top the first time, and caches the result. `id: 'python'` names the sandbox in the cell key.

## Add tools with install

```ts title="evals/jq.es.ts"
const withJq = docker({
  install: [
    'apt-get update && apt-get install -y --no-install-recommends jq ' +
      '&& rm -rf /var/lib/apt/lists/*',
  ],
})

evaluate('summarises a JSON file with jq', { sandbox: withJq }, async (t) => {
  // …
  await expect(t.exec('jq --version')).toSucceed()
  await expect(t.exec('./count.sh')).toSucceed()
})
```

`install` runs its commands in order, as root, in one build container, with `HOME` set to `/home/es`: what an installer puts in `~` is where the agent runs, and ES hands it to the `es` user. ES caches the result as one image, keyed on the base image and the exact list, so any edit builds anew. Install commands never see secrets or the workspace; anything that needs them is an environment `setup` step.

## Bring a Dockerfile

```dockerfile title="docker/sqlite/Dockerfile"
ARG ES_BASE
FROM ${ES_BASE}

RUN apt-get update \
  && apt-get install -y --no-install-recommends sqlite3 \
  && rm -rf /var/lib/apt/lists/*

COPY seed.sql /opt/seed.sql
```

```ts title="evals/sqlite.es.ts"
evaluate(
  'queries a seeded SQLite database',
  { sandbox: docker({ dockerfile: '../docker/sqlite/Dockerfile' }) },
  async (t) => {
    // …
    const report = await t.exec('sqlite3 app.db < report.sql')
    await expect(report).toSucceed()
    expect(report.stdout).toBe('Ada\nGrace\nLinus\n')
  },
)
```

ES builds the Dockerfile from its directory with `docker build`, and passes `ES_BASE`: its own image for the harness. `FROM ${ES_BASE}` layers on it, so the result already has the harness and is used as is. From any other Debian or Ubuntu base, ES adds the harness on top, as it does for `from`.

<Warning>
  Keep `root` as the user and leave `/es` alone in your Dockerfile. `RUN` lines build as root, but the agent runs as the `es` user (see [Sandbox security](#sandbox-security)), so install tools system-wide or under `/home/es` and `chown` them to `es`. `install` doesn't combine with `dockerfile`: write the commands as `RUN` lines.
</Warning>

## Build the images

```bash
npx es image build --dry-run
```

docker:sqlite · 1 eval
  dockerfile docker/sqlite/Dockerfile  evalsuite-dockerfile:sqlite-9630558fd3724574  (docker build (layer cache), tagged by content hash)
  harness                              evalsuite-dockerfile:sqlite-9630558fd3724574  (inherited: FROM ${ES_BASE}, which is evalsuite-sandbox:cursor-0.1.0)

`es image build` builds every image the planned evals need, per harness. Without it, `es run` builds `from`, `dockerfile` and `install` images on first use, once, while other attempts wait. Filters, `--tag` and `--profile` apply, as for `es run`.

## Sandbox security

The agent runs code you didn't write, so each container is locked down by default. You don't need to set anything up for this.

**What's isolated**

- **Your keys.** The harness's API key and brokered secrets never enter the container. The agent sees a placeholder, and the egress gateway on your machine swaps in the real value on the way out, only to that secret's hosts. See [credential brokering](/concepts/credential-brokering).
- **The network.** Under a restricted [egress policy](/guide/secrets-and-egress) the container is detached from every Docker network, so the gateway is its only way out. The agent can't change that: it can't edit routes or firewall rules, and unsetting or changing the proxy variables finds no other route. The gateway's process inside the container runs as root, so the agent can't stop or replace it either.
- **Privileges.** The agent, setup steps and `t.exec` checks run as `es` (uid 10001, home `/home/es`), not root. Every Linux capability is dropped and `no-new-privileges` is set, so setuid programs can't raise privileges. Image builds (`install`, your Dockerfile, `from`) still run as root.
- **Resources.** A runaway agent or fork bomb hits the container's limits, not your machine:

| Limit | Default | Option |
|---|---|---|
| Memory | 4 GB, with no swap on top. A process past it is killed (exit 137); the container keeps running | `memory: '8g'` |
| CPUs | 2, or fewer if the Docker host has fewer | `cpus: 4` |
| Processes and threads | 1024 | `pids: 4096` |

**What isn't isolated**

- **It's a container, not a VM.** It shares your machine's kernel. The steps above make a kernel or Docker bug much harder to reach, but they aren't a hardware boundary.
- **Under `allow-all`, the agent can reach anything.** That's the default when no eval sets a policy. The keys are still brokered, but the agent can go around the proxy to any host.
- **WebSocket messages aren't scrubbed.** Headers are, but if a brokered host echoes a real secret back inside a WebSocket message after the upgrade, the agent can read it.
- **Secrets sent `to: 'checks'` are real values in setup steps and checks.** Those run as the same `es` user as the agent, so a process the agent left running could read them while they run.

**When an eval needs more**

- **Root at run time**, for example an agent that has to `apt-get install` during the task. Use `docker({ root: true })`. The agent, setup and checks then run as root with only the capabilities `apt-get` needs (`CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETUID`, `SETGID`). Prefer baking packages in with `install`, which needs no opt-in.
- **A specific capability**, such as `NET_RAW` for `ping`. Use `docker({ capabilities: ['NET_RAW'] })`.

Either one is printed at the start of every run that uses it, naming where it was set, and kept in the run record:

```text
WARNING: running as root in the sandbox: evaluate("installs deps") (docker({ root: true }))
warning: extra capabilities in the sandbox: es.config.ts (docker({ capabilities: ['NET_RAW'] }))
```

Everything else works as the `es` user: `npm i`, `pip install` (as a user install), `git`, `curl`, and `npm i -g`, which goes to `~/.local`, on `PATH`.

## One sandbox per eval

An eval has one sandbox, and every attempt gets a fresh container from its image. Comparing toolchains means different checks (`python3 -m unittest` against `node --test`), so write a separate eval for each. The sandbox is still part of each cell's key, such as `cursor:composer-2.5/-/python`.
