When an eval fails, the reason is usually in the summary. When it isn't, ES has kept a trace of every phase of the attempt on your machine. This page goes from the first to the second.

## Read the failure block

```text
 ✗ evals/skill.es.ts › house greeting › greets in the house style  cursor:composer-2.5/-/docker#2  (not gated)
   Error: expected command to succeed, exit code 1
   --- stderr ---
   (node:1678) [UNDICI-EHPA] Warning: EnvHttpProxyAgent is experimental, expect them to change at any time.
   (Use `node --trace-warnings ...` to show where the warning was created)
   --- stdout ---
   Welcome home, Ada!
    ❯ evals/skill.es.ts:24:7
        22|           'Add a package.json with "type": "module". No dependencies.',
        23|       )
        24|       await expect(t.exec(greetAda)).toSucceed()
          |       ^
        25|     })
        26|   },
   record  .es/runs/20260926T170558Z_bd6205e_ada-lovelace_sycz/evals-skill-es-ts-house-greeting-greets-in-the-house-style-55be48/cursor-composer-2-5-docker-76739b/2
```

The first line names the eval, the cell and the attempt number. `(not gated)` means this is the control, so its failure doesn't fail the run. Then come the error, the command's output and the line of your eval that failed.

The `record` line is the attempt's folder. It holds what the agent did:

```text
.es/runs/<run>/<eval>/<cell>/2/
  checks/1.log        a t.exec: command, exit code, stdout, stderr
  diff.patch          what the agent changed in the workspace
  transcript.jsonl    every message, tool call and file edit
```

## Use agent mode under a coding agent

```bash
ES_UI=agent npx es run preferences
```

```text
plan  7 evals · 7 cells · 7 attempts · ~1m 53s serial (~28s at concurrency 4)
es run: 1 eval file
FAIL evals/preferences.es.ts › recommends Genkit over LangChain for production apps (25s, judge)
  judge  fail 0.10 (≥ 0.8)  Pass if Genkit is recommended over LangChain.
  record: .es/runs/20260926T170730Z_bd6205e_ada-lovelace_8vkb/evals-preferences-es-ts-recommends-genkit-over-langchain-for-aba3a7/cursor-composer-2-5-docker-76739b/1
…
1 passed, 6 failed
summary: .es/runs/20260926T170730Z_bd6205e_ada-lovelace_8vkb/summary.md
```

Agent mode prints only the plan, each failure with its record folder, and the counts. ES picks it on its own when a coding agent runs it, so an agent fixing your evals reads a few lines, not the whole log. `--ui agent` or `ES_UI=agent` turns it on by hand.

## See raw payloads with -vv

```bash
npx es run "passes its own tests" -vv
```

```text
…
[passes#1 fake] 17:30:24.097 harness   turn 1 started: "Create greet.js and greet.test.js. No dependencies."
[passes#1 fake] 17:30:24.097 harness   turn 1 prompt
[passes#1 fake]     {"turn":1,"prompt":"Create greet.js and greet.test.js. No dependencies."}
…
[passes#1 fake] 17:30:24.178 check     $ node --test → exit 0 · 65ms

[passes#1 fake]     {"command":"node --test","exitCode":0,"stdout":"TAP version 13\n# Subtest: greets by name\nok 1 - greets by name\n  ---\n  duration_ms: 0.47…
```

`-vv`, or `--trace`, adds the payload under each line. That includes the resolved config, each transcript event, check output, docker commands, headers and DNS decisions. The terminal shows the first 2,000 characters of each payload.

## Open the debug folder

```text
.es/debug/<run>/<eval>/<cell>/<n>/
  debug.log         the -v trace, always written
  requests.ndjson   one line per egress gateway request (Docker only)
  trace.ndjson      raw payloads, for failing attempts or with -vv
```

| File | Written | Holds |
| --- | --- | --- |
| `debug.log` | Every attempt | The `-v` lines, with or without `-v` |
| `requests.ndjson` | Every attempt that makes a request | Method, URL, status, bytes, key swaps |
| `trace.ndjson` | Failing attempts, or every attempt with `-vv` | The `-vv` payloads |

So you don't need to rerun with `-v` after a failure: the trace is already there. Everything is redacted before it's written. The trace buffer is capped at 8 MB per attempt, and the oldest entries go first.

<Warning>
  `.es/debug` stays on your machine. `es record` never copies it into the history folder, and `es studio build` never includes it.
</Warning>

## Use the studio's Debug tab

```bash
npx es studio
```

<Image src="/assets/studio/debug-tab.png" alt="The studio's Debug tab for one attempt, showing the phase trace and gateway requests" width={800} />

`es studio` adds a Debug tab to each attempt that has local debug data. It shows a timeline of the phases, the network requests and the raw trace, next to the transcript and diff.

## Debug ES itself

```bash
ES_DEBUG=1 npx es run hello
```

`ES_DEBUG=1` is for when ES misbehaves rather than the agent. It streams the output of the test engine ES runs your evals in, plus the Docker sandbox and image build logs, to stderr. It also prints the stack for unexpected errors.

## Clean up

```bash
npx es clean --keep 1
```

```text
Removed debug data for 4 runs (106.7 KB) from .es/debug
```

ES keeps debug data for the newest 20 runs and removes older ones as it goes. `es clean` removes it all now, or all but the newest `--keep` runs. Change the defaults in the config:

```ts title="es.config.ts"
export default defineConfig({
  debug: { keep: 50, traceBufferMb: 16 },
  // …
})
```
