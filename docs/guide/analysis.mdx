---
title: Analysis
description: Ask your eval history questions in SQL with reeval query, and get a checked, plain-words reading of a run with reeval analyze.
---

reeval gives you two ways to dig into results. `reeval query` runs read-only SQL over every recorded and scratch run, and its answers are computed by fixed rules. `reeval analyze` makes one LLM call over those same facts and explains the run in plain words, with every claim checked.

```bash
npx reeval query
```

```text
history.db: 9 runs
Views (the common questions; filter them with SQL):
  drift(run_id, prev_run_id, eval_key, cell_key, changed, changed_paths, noise, real_changed)
  effort(run_id, eval_key, cell_key, role, variant, harness, environment, n, tools_median, …)
  eval_trend(eval_key, run_id, started_at, branch, pr_number, recorded, outcome, pass_rate, fingerprint)
  factor_effects(factor, level, baseline, context, tier, run_id, eval_key, strata, runs, …)
  failing_attempts(run_id, started_at, eval_key, attempt_key, cell_key, harness, model, …)
  flaky_cells(eval_key, cell_key, fingerprint, runs, flaky_runs, first_seen, last_seen, …)
  lift(run_id, started_at, branch, eval_key, harness, model, variant, control, …)
  skill_reads(run_id, eval_key, cell_key, attempt_key, attempt_id, variant, skill, placement, read_line, reads)
  verdict_flips(run_id, prev_run_id, eval_key, cell_key, judgement_key, question, prev_pass_rate, pass_rate, n)
…
```

With no argument, `reeval query` lists the views, the tables and a few examples. A view is a common question with the joins done for you. Filter it with SQL like any table. The history here is the runs from the earlier pages, including the two house-greeting compares.

## Track lift over time

```bash
npx reeval query "SELECT eval_key, harness, variant, variant_pass,
  variant_counted, control_pass, control_counted, points, lo, hi,
  within_noise FROM lift"
```

```text
history.db: 9 runs
```

## Measure effort

```bash
npx reeval query "SELECT eval_key, cell_key, n, tools_median,
  control_tools_median, tools_ratio, tools_p, verdict
  FROM effort WHERE role = 'variant'"
```

```text
history.db: 9 runs
eval_key                                                   cell_key                                                      n  tools_median  control_tools_median  tools_ratio  tools_p  verdict
evals/skill.eval.ts › house greeting › greets in the house…  cursor:composer-2.5/with-house-greeting/docker                2  3             8                     0.375        0.3333   insufficient
evals/skill.eval.ts › house greeting › greets in the house…  cursor:composer-2.5/with-house-greeting/docker                2  3             11.5                  0.2609       0.3333   insufficient
evals/skill.eval.ts › house greeting › greets in the house…  antigravity:gemini-3.8-flash-medium/with-house-greeting/doc…  2  3.5           24.5                  0.1429       0.3333   insufficient
```

`effort` is the summary's effort line as data: median tool calls and agent time for each cell, and for a variant, its control's. `tools_p` is an exact rank test. With two attempts a side it can never drop below 0.05, so every row is `insufficient`, however large the gap.

## Pool runs to separate the factors

```bash
npx reeval query "SELECT factor, level, tier, runs, points, lo, pass_verdict,
  tools_p, effort_verdict FROM factor_effects
  WHERE factor = 'environment'"
```

```text
history.db: 9 runs
factor       level                tier        runs  points  lo     pass_verdict  tools_p  effort_verdict
environment  with-house-greeting  controlled  1     1       0.07   effect        0.3333   insufficient
environment  with-house-greeting  controlled  1     1       0.07   effect        0.3333   insufficient
environment  with-house-greeting  controlled  1     1       0.07   effect        0.3333   insufficient
environment  with-house-greeting  pooled      2     1       0.307  effect        0.0286   fewer
```

`factor_effects` asks what one factor (the environment, the harness or the model) changes, and says how good the evidence is. `controlled` compares two cells in one run. `pooled` combines the same comparison over comparable runs. Pooling Cursor's two compares gives four attempts a side, enough to call the skill's saving `fewer` tool calls.

## Check that the agent read the skill

```bash
npx reeval query "SELECT cell_key, skill, read_line, reads FROM skill_reads"
```

```text
history.db: 9 runs
cell_key                                                      skill           read_line  reads
cursor:composer-2.5/with-house-greeting/docker                house-greeting  4          1
…
antigravity:gemini-3.8-flash-medium/with-house-greeting/doc…  house-greeting  2          1
```

`skill_reads` has one row per attempt and skill its environment placed. `read_line` is the line in `transcript.jsonl` of the first tool call on the skill's folder, and it's null, with `reads` at 0, when the agent never opened it. A variant that passes without reading its skill didn't pass because of it.

## Count tokens

```bash
npx reeval query "SELECT c.role, a.served_model, COUNT(*) AS n,
  round(AVG(a.input_tokens)) AS input, round(AVG(a.output_tokens)) AS output
  FROM attempts a
  JOIN cells c ON c.run_id = a.run_id AND c.eval_key = a.eval_key
    AND c.key = a.cell_key
  WHERE c.eval_key LIKE 'evals/skill.eval.ts%' AND c.harness_kind = 'cursor'
  GROUP BY c.role, a.served_model"
```

```text
history.db: 9 runs
role     served_model             n  input  output
control  composer-2.5[fast=true]  4  92569  1458
variant  composer-2.5[fast=true]  4  33045  494
```

The `attempts` table has each attempt's tokens and the model that served it. With the skill, Cursor used about a third of the tokens. `served_model` shows the parameters too: with no `params` set, `composer-2.5` ran as `fast=true`. A cell's key repeats across evals in a run, so join `cells` on `eval_key` as well.

## Script it and rebuild it

```bash
npx reeval query "SELECT harness, points, lo FROM lift
  WHERE within_noise = 0" --json
```

```text
[
  {
    "harness": "cursor:composer-2.5",
    "points": 1,
    "lo": 0.07
  },
…
]
```

`--json` prints the rows as JSON, and the `history.db:` line goes to stderr, so the output pipes cleanly into `jq` or a script. `--schema` lists every table and column.

The database, `.reeval/history.db`, is a cache built from the run records and brought up to date on every query. It's read-only:

```text
reeval: reeval query is read-only: .reeval/history.db is a projection of the run records (attempt to write a readonly database)
```

`--rebuild` throws it away and reads every record again.

## Explain a run with reeval analyze

```bash
npx reeval analyze --config reeval.agents.config.ts --save
```

```text
analysing 20260926T174444Z_b010670_ada-lovelace_7gmj vs 20260926T174239Z_b010670_ada-lovelace_yzmg with google/gemini-3.8-flash…
…
Results
  - For eval 'skill', the house-greeting skill produced a controlled pass-rate lift of +100 pts (95% CI +7…+100, verdict: effect) in both cursor:with-house-greeting and antigravity:with-house-greeting relative to their respective control cells. [F5…
…
  - Within run r2 alone, effort reductions on eval 'skill' (cursor: 3 vs 11.5 tool calls; antigravity: 3.5 vs 24.5 tool calls; p = 0.3333 for both) had a verdict of insufficient because 2 vs 2 attempts cannot reach statistical significance. [F10]
…
Suggested actions
  1. Increase attempt count on skill eval to reach statistical power for effort (eval · impact medium · effort low) [F10] [F11]
     target: evals/skill.eval.ts. Run more attempts per cell (at least 6 per cell) so exact Mann-Whitney effort tests can achieve p < 0.05 significance rather than returning insufficient.
     expect: Effort differences (fewer tool calls and agent seconds) reach statistical significance instead of insufficient.
     verify: reeval run --runs 6 --tag skill
…
gemini-3.8-flash · analysis-v2 · digest v1 · 10381 in / 3196 out tokens · 13s · 29 citations checked, 0 invalid, 0 dropped · 1 commands checked, 0 rejected
```

`reeval analyze` explains the latest run against its nearest recorded ancestor, here the cross-agent run from [Harnesses](/guide/harnesses): what happened, the results, why, anomalies, and at most five actions.

reeval computes the facts, the model only explains them, and every claim must cite a fact (`F…`) or evidence (`E…`) from the digest. reeval drops claims that don't, flags numbers no cited fact holds, and rejects any verify command its CLI wouldn't parse. The footer counts all three; an `insufficient` lift or effort verdict is not measured, so it is not a results line.

<Warning>
  A check doesn't make a claim right. Here the verify command parses, but `evals/skill.eval.ts` has no `skill` tag, so it would run nothing. Read each action before you act on it.
</Warning>

## Check it, cache it, save it

```bash
npx reeval analyze --config reeval.agents.config.ts --dry-run
```

```text
digest 20260926T174444Z_b010670_ada-lovelace_7gmj vs 20260926T174239Z_b010670_ada-lovelace_yzmg: 24 facts, 5 evidence items, 18 attempts
size 26510 characters ≈ 6628 tokens (cap 20000 in, 8000 out)
model google/gemini-3.8-flash · analysis-v2 · cache miss (.reeval/analysis/cb4f1ade460a94fdd4e5a9ddef213bd995e81adbbf4f83d0c4a7fa93e0a69398.json)
```

`--dry-run` shows the digest's size and the cache key without a call. The same inputs never call the model twice: `.reeval/analysis` caches each answer, and `--no-cache` asks again. `--save`, as above, also writes it into the run's history folder as JSON and Markdown, to commit. `--md` and `--json` print it for a PR comment or a script.

`--context` needs no key and makes no call. It prints the digest and reeval's rules as Markdown, for your own coding agent to read. To choose the model or steer it, set `analysis` in the config:

```ts title="reeval.config.ts"
export default defineConfig({
  analysis: {
    model: 'google/gemini-3.8-flash', // default: the judge's, if it can
    instructions: 'Fewer tool calls count as a win.',
  },
  // …
})
```

## Notes during a run

```ts title="reeval.config.ts"
export default defineConfig({
  analysis: { agent: true, model: 'google/gemini-3.8-flash' },
  // …
})
```

```text
analysis: 1 note in .reeval/analysis/20260929T201657Z_33d6cda_cursor-agent_dr8k/notes
```

With `agent: true`, `reeval run` writes a note on each eval and harness as soon as that harness's attempts of the eval have all finished. The model doesn't read whole transcripts. It gets tools: list the attempts, open one, and compare a failed attempt with a passing one to see where their steps diverged.

```json title=".reeval/analysis/<runId>/notes/<eval>__<harness>.json"
{
  "kind": "reeval-analysis-note",
  "evalId": "evals/skill.eval.ts › house greeting › greets in the house style",
  "harness": "fake",
  "model": "google/gemini-3.8-flash",
  "attempts": ["fake/plain/fake#1", "fake/with-house-greeting/fake#1"],
  "text": "In fake/plain/fake#1, the agent failed the assertion check because `greet('Ada')` returned \"Hello, Ada!\" rather than the expected \"Ahoy, Ada!\". In contrast, fake/with-house-greeting/fake#1 passed with the expected greeting. …",
  "usage": { "inputTokens": 5768, "outputTokens": 549 },
  …
}
```

A note never changes an outcome or the exit code. If the call fails, the note keeps its `error` and the run prints a warning. `agent` is off by default because it's one more model call per eval and harness on every run; `maxInputTokens` and `maxOutputTokens` cap each one.

```text
…
gemini-3.8-flash · analysis-v2 · digest v1 · 15493 in / 4862 out tokens · 18s · 33 citations checked, 0 invalid, 0 dropped · 2 commands checked, 0 rejected
```

Once the run is written, `agent: true` also summarises it: the document `reeval analyze` writes, against the same base and under the same cache key. So `reeval analyze` prints it with no call, and `--save` keeps it in the history folder. Before its answer, the model can read what the digest left out with tools: evidence dropped to fit `maxInputTokens`, and any attempt's steps, checks and diff.

If the summary's call fails, the cache keeps it with its `error` and the run prints a warning; the exit code stands. `reeval analyze` counts a failed summary as a miss and asks again. The studio's Analysis tab shows the summary, each harness's notes, and a failed call's error:
