title: reeval query
description: Read-only SQL over every recorded and scratch run, with every view and table.
---

`reeval query` answers questions across runs with SQL. It reads `.reeval/history.db`, a gitignored SQLite projection of every record in the history folder and `.reeval/runs/`.

```bash
npx reeval query lift
npx reeval query "SELECT eval_key, variant, points, lo, hi FROM lift
  WHERE within_noise = 0"
```

```text
  --json                      Rows as JSON; --schema every table and column; --rebuild from scratch
```

## Behaviour

- **Argument:** a view or table name runs `SELECT * FROM <name>`. Anything else is a SQL statement. No argument lists the views and tables with examples. An unknown name exits 2 listing both.
- **SQL from a file:** `reeval query "$(cat q.sql)"` works when the file opens with a `-- comment`: an argument with whitespace before any `=` is SQL, never a flag. `--json`, `--schema`, `--rebuild` and `--run` go before or after it, and `--` ends option parsing: `reeval query --json -- "<sql>"`.
- **`--run <id|last>`** binds a run id to the named parameter `:run` (`$run` and `@run` work too). `last` (or `latest`) is the run with the newest `started_at` in `history.db`; an id may be a unique prefix. reeval never rewrites your SQL: a statement that uses `:run` without `--run`, or `--run` with a statement that doesn't use `:run`, exits 2. With a bare view or table name, `--run` runs `SELECT * FROM <name> WHERE run_id = :run`; `flaky_cells` pools runs and has no `run_id`, so it refuses `--run`.
- **Read-only, one statement at a time.**
- **Always current:** each query re-reads only records that are new or changed. A recorded run wins over its scratch copy. `--rebuild` rebuilds the database from scratch, and you can delete it at any time.
- **Output:** an aligned table, or JSON rows with `--json`. The table clips a long value to 60 characters with `…`, except a `sql` column (`sqlite_schema.sql`, each CREATE statement), which prints in full; `--json` has every value whole. The sync line (`history.db: 13 runs`) goes to stderr, so output pipes cleanly.
- **Needs** Node 22.13 or later (`node:sqlite`).

A real query (`points`, `lo` and `hi` are fractions: 1 is +100 points):

```text
eval_key                                                   harness                              variant              variant_pass  variant_counted  control_pass  control_counted  points  lo    hi  within_noise
…
evals/skill.eval.ts › house greeting › greets in the house…  cursor:composer-2.5                  with-house-greeting  2             2                0             2                1       0.07  1   0
```

The last run's evals, with `--run`:

```bash
npx reeval query "SELECT key, outcome FROM evals WHERE run_id = :run" \
  --run last
npx reeval query failing_attempts --run last
```

In the text table, `·` is SQL `NULL`; `--json` has `null`. On `factor_effects`, a `pooled` row has `run_id` `NULL` (it spans runs), and a row pooled across evals (with `strata` set and `runs` `NULL`) has `eval_key` and `runs` `NULL` too.

Several views repeat a cell's key across evals in a run, so join `attempts` and `cells` on `eval_key` as well as `cell_key`; on `cell_key` alone each attempt matches every eval's cell of that key and is counted once per eval.

## Per-cell rates

`lift` pools each attempt's pass, every check at once. `check_rates` gives one labelled check's rate per cell, here from a project of greeting evals on the fake harness:

```bash
npx reeval query "SELECT cell_key, role, label, pass, fail, rate
  FROM check_rates WHERE label = 'house greeting'"
```

```text
cell_key                       role     label           pass  fail  rate
fake/plain/fake                control  house greeting  0     1     0
fake/with-house-greeting/fake  variant  house greeting  1     0     1
…
```

Adoption, whether an arm used what its environment gave it, is the share of counted attempts with at least one `context` call in `context_use` (a placed skill, rules file or MCP tool of the environment). The `LEFT JOIN` keeps attempts with no such call, so they count as not adopted. Here on the harness contract's recorded runs on Cursor, Claude Code and Codex:

```bash
npx reeval query "SELECT a.eval_key, a.cell_key, COUNT(*) AS attempts,
  COUNT(u.attempt_key) AS adopted,
  CAST(COUNT(u.attempt_key) AS REAL) / COUNT(*) AS adoption
FROM attempts a
LEFT JOIN context_use u ON u.run_id = a.run_id
  AND u.attempt_key = a.key AND u.class = 'context'
WHERE a.outcome IN ('pass', 'fail')
GROUP BY a.run_id, a.eval_key, a.cell_key"
```

```text
eval_key                        cell_key                                     attempts  adopted  adoption
…
evals/mcp.eval.ts › mcp         claude-code:claude-haiku-4-5/stamped/docker  1         1        1
evals/mcp.eval.ts › mcp canary  claude-code:claude-haiku-4-5/stamped/docker  1         0        0
evals/skill.eval.ts › skill     codex:gpt-5.4-mini/skilled/docker            1         1        1
…
```

For one MCP server or one shell command, match `tool_calls` instead: an MCP tool is `mcp__<server>__<tool>`, and a shell command's `target` is its command line (`t.target LIKE '%<cli> <subcommand>%'`):

```bash
npx reeval query "SELECT a.eval_key, a.cell_key,
  COUNT(DISTINCT a.key) AS attempts, COUNT(DISTINCT t.attempt_key) AS used
FROM attempts a
LEFT JOIN tool_calls t ON t.run_id = a.run_id AND t.attempt_key = a.key
  AND t.tool LIKE 'mcp__stamp__%'
GROUP BY a.run_id, a.eval_key, a.cell_key"
```

```text
eval_key                        cell_key                                     attempts  used
…
evals/mcp.eval.ts › mcp         cursor:composer-2.5/stamped/docker           1         1
evals/mcp.eval.ts › mcp canary  cursor:composer-2.5/stamped/docker           1         0
…
```

The tables mirror [the run record](/reference/record) and join on `run_id` plus the keys below. A table's own key is plain `key` (or `digest`), so most joins pair differently named columns:

| Column | Joins | Also on |
|---|---|---|
| `cells.eval_key`, `attempts.eval_key` | `evals.key` | `run_id` |
| `attempts.cell_key`, `assertions.cell_key`, `cell_checks.cell_key`, `families.cell_key` | `cells.key` | `run_id`, `eval_key` (`families`: its cases' evals) |
| `cells.lift_vs` | `cells.key` of the control | `run_id`, `eval_key` |
| `judgements.attempt_key`, `assertions.attempt_key`, `tool_calls.attempt_key`, `artifacts.attempt_key`, `attempt_context.attempt_key`, `context_reads.attempt_key` | `attempts.key` | `run_id` |
| `cells.environment_digest` | `environments.digest`, `env_skills.digest` | `run_id` |
| `evals.family_id` | `families.family_id` | `run_id` |

```sql
SELECT a.key, c.harness, e.name
FROM attempts a
JOIN cells c ON c.run_id = a.run_id AND c.eval_key = a.eval_key
  AND c.key = a.cell_key
JOIN evals e ON e.run_id = c.run_id AND e.key = c.eval_key
WHERE a.run_id = :run
```
